## Fresh production cutover

1. Confirm the intended region/data handling, final Netlify domain, and cost ceiling. Production will use the existing Sydney EC2 host and 00:00–07:00 Asia/Kolkata shutdown. Keep staging and production runtime settings separate, even though the host is shared. Plan the preview's loss of backend isolation at cutover.
2. **Database prepared:** `aitherapy_production` exists and has verified successful Flyway V1–V10 history with zero application rows. Keep application startup migrations disabled. Configure the production runtime to use this exact database and verify application readiness against it; do not point production at `neondb` or `aitherapy_staging`.
3. Store production-only JWT, encryption, database, Redis and Google settings in `/aitherapy/production/runtime-env` (SSM SecureString). Store the Razorpay Live Mode ID, API secret and separate webhook secret in `/aitherapy/production/razorpay-key-id`, `/aitherapy/production/razorpay-key-secret` and `/aitherapy/production/razorpay-webhook-secret` (three SecureString parameters). The production startup script rejects Razorpay credentials in the runtime JSON and reads the three dedicated parameters without logging their values. Extend the EC2 role's narrowly scoped read policy to this path through its CloudFormation stack; validate the change set before applying it. Use a distinct OAuth callback on the final Netlify domain, configure exact CORS origins, and verify ticket handoff, refresh, logout and account deletion. Never copy staging test keys into production.
4. Submit the public production website for Razorpay verification, including an agreed reviewer login method, and wait for approval before generating live API credentials. Configure a live `payment.captured` webhook and a distinct matching secret at the stable production Netlify HTTPS route. Check key mode without exposing keys, signed webhook verification, capture behavior and ₹100 (10,000 paise) order creation. A real payment requires a separately agreed purchase/reconciliation procedure. Because the backend shuts down overnight, disable new checkout before shutdown and reconcile late payments/webhook retries after startup; monitor the webhook's delivery status.
5. Build a production frontend from the accepted commit against the verified production API and OAuth endpoints. Keep preview-only redirects and the staging IP out of that build. Confirm that Netlify production deploy settings, OAuth callback, sitemap and canonical URL match the chosen domain.
6. Run synthetic end-to-end acceptance on production before inviting users: sign-in, onboarding, free chat, streaming recovery, memory actions, usage limits, checkout in the intended provider mode, account deletion, mobile layout and reduced motion. Verify backups, alerts, rollback image, schema version and a known-good Netlify deploy before switching public traffic.
