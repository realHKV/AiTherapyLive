# Step 15 — AWS demo infrastructure prepared

**Status:** code prepared and locally validated; no AWS account changes or deployment. Region: `ap-south-1` (Mumbai). Frontend: Netlify. API: the default HTTPS `*.awsapprunner.com` URL. The user requested no purchased domain and no separately provisioned load balancer, with one warm instance for a responsive demonstration and minimal fixed cost.

## Why this design

The previous ECS Fargate plan needed public ingress and private data networking. An ALB, NAT gateway, RDS and ElastiCache each add idle charges; a task public IP alone has no stable HTTPS hostname. App Runner supplies an AWS HTTPS hostname and keeps one provisioned instance warm. It accepts ECR images, so the reviewed private Docker Hub image is copied to private ECR without rebuilding. It has a 120-second total HTTP request limit; the current v2 chat stream timeout is 90 seconds, but real SSE flushing must be checked in Step 16. App Runner has no separately billed ALB in this Terraform stack. [App Runner pricing](https://aws.amazon.com/apprunner/pricing/), [HTTP timeout](https://docs.aws.amazon.com/apprunner/latest/dg/develop.html), [ECR image requirement](https://docs.aws.amazon.com/apprunner/latest/dg/service-source-image.html).

The demo stack intentionally uses a **separate external demo PostgreSQL and Redis** with TLS and synthetic data. Existing Render/Upstash infrastructure is a possible source, but the live database must not be migrated or exposed to tests by default. App Runner's default outbound access reaches external providers, Google, Razorpay and Bedrock without a customer NAT gateway. If the database is private or blocks the GitHub runner, the migration workflow cannot reach it; select a suitable demo database before apply. A serverless database that sleeps can still cause a slow first request, so a warm App Runner instance alone cannot guarantee every request is wait-free. [App Runner outbound networking](https://docs.aws.amazon.com/apprunner/latest/dg/network-vpc.html).

## Delivered files and controls

- [`infra/demo`](../../infra/demo/main.tf): Terraform creates ECR, App Runner, one warm instance with a two-instance cap, ECR access and app instance roles, a GitHub OIDC deployment role, cost budget, SNS email alert, and 5xx alarm. App Runner writes application and deployment logs to CloudWatch automatically. The runtime role can read only configured secret ARNs and invoke only approved Bedrock resources. The GitHub role can mirror into one ECR repo, update one App Runner service, and read only migration settings. Terraform creates no VPC, ALB, NAT, RDS, ElastiCache, frontend bucket, EC2 server or cluster.
- [`backend-demo-deploy.yml`](../../../.github/workflows/backend-demo-deploy.yml): manual, serialized, protected `backend-demo` environment; accepts only `codex/backend-baseline` or `main`. It uses OIDC, no long-lived AWS key. The script checks successful source CI and release runs, Docker Hub digest and platform, then copies to ECR. The destination ECR digest is recorded separately because a registry copy can change the manifest digest.
- [`demo-release.sh`](../../deploy/demo-release.sh) and [`demo-update.sh`](../../deploy/demo-update.sh): `bootstrap` mirrors the image and runs the migration-only container. `deploy` also updates App Runner, waits for the deployment operation, checks readiness, and restores the prior image/configuration on failure. Database schema migrations are never automatically reversed. Terraform ignores later image changes so the release workflow owns them.
- [`backend-tests.yml`](../../../.github/workflows/backend-tests.yml): no-credential Terraform format/init/validate gate.

The application uses at most 10 PostgreSQL connections per instance; the two-instance cap means up to 20 app connections plus migration/admin headroom. App Runner HTTPS terminates at the managed edge. The production profile still requires `DATABASE_URL` with `sslmode=verify-full`, remote Redis with `REDIS_SSL=true` and a password, valid signing/encryption keys, exact HTTPS CORS origins, and Bedrock/v2 flags. Preserve the existing `ENCRYPTION_MASTER_KEY` for any restored encrypted records and JWT keys if token continuity is required. Secret values live in AWS Secrets Manager or SSM SecureString and are injected by ARN; Terraform state holds references, not secret values. The one-off migration has a separate DDL user/password reference from the app runtime credentials. Rotation needs an App Runner redeployment. [App Runner secrets](https://docs.aws.amazon.com/apprunner/latest/dg/env-variable.html).

## AWS setup and first deployment (not performed)

1. In AWS Billing, verify the actual credit balance/expiry and account plan. Set a billing alert email. Terraform defaults to a **$15/month alert budget**, with notifications at 50% actual and 80% forecast. This is an alert, not a spending cap; Bedrock usage and external providers can add cost. The account plan and Mumbai prices should be checked in the AWS Pricing Calculator before creating the warm service. [Free Tier credit rules](https://aws.amazon.com/free/free-tier-faqs/), [budget pricing](https://aws.amazon.com/aws-cost-management/aws-budgets/pricing/).
2. Set up AWS CLI authentication with IAM Identity Center or another short-lived administrator session. Do **not** paste AWS keys in chat or GitHub secrets. Create a private, encrypted, versioned S3 bucket for Terraform state only; Netlify continues to host the frontend. Initialize `Backend/infra/demo` with that bucket and key using `terraform init -backend-config=...`; protect state access and never commit `.tfstate`, `.tfvars` or a saved plan.
3. Prepare an isolated demo PostgreSQL and Redis with synthetic data. Confirm PostgreSQL `sslmode=verify-full` from the image and GitHub runner, and Redis TLS/auth from App Runner. Use a compatible root certificate path if the chosen PostgreSQL provider needs one. Create a DDL user for migration and a separate data-access user for the application; grant each only its required permissions.
4. Create individual Secrets Manager secrets or SSM SecureString parameters in `ap-south-1` for `DATABASE_URL`, runtime `DATABASE_USER`/`DATABASE_PASSWORD`, migration `DATABASE_USER`/`DATABASE_PASSWORD`, `REDIS_HOST`, `REDIS_PASSWORD`, `JWT_PRIVATE_KEY`, `JWT_PUBLIC_KEY`, `ENCRYPTION_MASTER_KEY`, `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `RAZORPAY_KEY_ID`, `RAZORPAY_KEY_SECRET`, `RAZORPAY_WEBHOOK_SECRET`, and `CORS_ALLOWED_ORIGINS`. Use the exact Netlify HTTPS origin as the CORS value; do not include a path. Keep secret *values* out of Terraform/GitHub. Put only runtime ARNs in local `secret_arns`, and DDL ARNs in `migration_secret_arns`, in an ignored `.tfvars` file. Select verified Mumbai Bedrock model IDs and exact model/inference profile ARNs.
5. Run the first Terraform apply with `create_service=false` **and all demo secret ARNs supplied** to create ECR, IAM and budget resources. Create the GitHub `backend-demo` environment, restrict it to the approved branch and require reviewer approval. Set environment variables `AWS_DEPLOY_ROLE_ARN`, `AWS_ECR_REPOSITORY_URL`, `DATABASE_URL_ARN`, `MIGRATION_DATABASE_USER_ARN`, `MIGRATION_DATABASE_PASSWORD_ARN`; set `DOCKERHUB_USERNAME` and a **separate read-only** `DOCKERHUB_READ_TOKEN` as environment secrets. GitHub's existing `backend-release` push token is not the App Runner/ECR pull credential.
6. Run **Backend demo deployment** with mode `bootstrap` using the committed Step 14 release manifest. Record its ECR digest only after the isolated demo migration succeeds. Update local Terraform variables with that ECR digest, `create_service=true`, all secret ARNs, approved Bedrock model IDs/ARNs, and the budget email; review the plan and apply. The service must pass `/api/v1/actuator/health/readiness` before use. Add output `service_arn` as `AWS_APPRUNNER_SERVICE_ARN` in the GitHub environment for later `deploy` runs.
7. In Netlify, set `VITE_API_BASE_URL=https://<service-url>/api/v1`. Register `https://<service-url>/api/v1/login/oauth2/code/google` as the Google OAuth callback and `https://<service-url>/api/v1/payment/webhook` as the Razorpay webhook. The frontend chat client has a known stream URL mismatch; Step 17/18 must fix it before full browser acceptance. Run the full Step 16 synthetic OAuth, payment, FREE/PRO, SSE, job, restart, and rollback checks before routing real users.
